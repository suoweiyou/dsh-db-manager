## 1. 背景与目标

### 1.1 现状（已核实）

| 事实 | 依据 |
|---|---|
| SSH 目前**只做端口转发** | `src/db/ssh-tunnel.ts:563` `client.forwardOut(...)`；全文件无 `exec` / `shell` |
| Host 侧无子进程能力 | `src/` 全库 `child_process` / `spawn` 0 命中 |
| 唯一"命令"产物是给人复制的文本 | `manualSshCommand()` / `knownHostsFixHint()`（`ssh-tunnel.ts:271`、`:291`） |
| SSH 配置已有完整凭据/主机密钥体系可复用 | `sshProfileSchema`（4 种认证、严格 known_hosts）、`connectSsh()`、`probeSshProfile()` |

所以「让 db-manager 连服务器看日志」在现有代码里**不可能**，需要新增能力，而不是打开某个开关。

### 1.2 目标

给 SSH 配置增加**日志源白名单**，并新增一条**只读、参数封闭**的日志读取通道：

1. **主用途（唯一必须做好的）**：对话中由模型读取白名单内的日志并带进上下文分析代码/接口问题，覆盖三步闭环：
   - **看有什么**：`db_list_ssh_logs` 列出各机器上登记过的日志源；
   - **读某个源**：`db_read_ssh_log` 取尾部 N 行（可带关键字）；
   - **顺着线索横向找**：`db_search_ssh_logs` 用同一个关键词一次性检索**多个**日志源（找到 `traceId`/错误码后，去其它日志文件里比对），返回带上下文的命中；
2. 运维/模型都能登记日志源：SSH 编辑器白名单字段，或**对话内** `db_add_ssh_log_source`（已确认纳入）；
3. 全程**没有任何任意命令执行入口**：不是"限制 shell 命令"，而是**根本不拼 shell**；
4. **不做**设置页的「查看日志」读取面板（理由见 §2.3）。

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 任意命令执行 / 交互式 shell / `sudo` | 等于给模型一个远程 shell，绕过全部既有护栏 |
| 上传、删除、改权限、编辑日志文件 | 只读原则；代码里不注册任何写类 SFTP 操作 |
| 目录遍历 / `ls` / 通配符白名单 | 白名单只认**精确文件路径**；目录级放行等于放开未知面 |
| 全文搜索整个日志（grep 全文件） | 需服务端 `grep`（= 命令执行）；改为"尾部窗口内本地过滤"，语义在文案里写明 |
| 日志内容落盘（导出/缓存/审计正文） | 日志常含密码、token、PII；读完即返回，不持久化 |
| 设置页「查看日志」读取面板（v1） | 鼠标点出来的日志**进不了对话**，与本能力的目的（模型读日志分析问题）无关；面板本身要多写 RPC + 面板状态 + 渲染用例（约 1 人日），先不做，见 §2.3 与 D7 |
| Windows 服务器日志（事件日志） | 目标为 POSIX；不支持的源直接报错，不做半成品 |
| 压缩日志 `.gz` 解压检索（v1） | 需整文件读取+解压，代价与内存风险高；见 D5 |

## 2. 使用形态（用户视角）

### 2.1 配置（`~/.dsh/db-manager/connections.json`）

```jsonc
{
  "sshProfiles": [
    {
      "name": "jump-prod",
      "host": "203.0.113.10", "port": 2222, "username": "deploy",
      "auth": { "method": "password", "password": "$ENV:SSH_PW" },
      // ↓ 本次新增：日志源白名单（不配 = 该机器没有日志能力）
      "logSources": [
        { "name": "app",        "kind": "file",    "path": "/var/log/app/app.log", "label": "应用日志" },
        { "name": "app-journal","kind": "journal", "unit": "app.service",          "label": "应用 journal" },
        { "name": "mysql-error","kind": "file",    "path": "/var/log/mysql/error.log",
          "via": "db-host-prod" }                    // ← 两跳：读跳板机之后的数据库机
      ]
    },
    {
      "name": "db-host-prod",
      "host": "198.51.100.30", "port": 22, "username": "ops",
      "auth": { "method": "keyfile", "keyPath": "~/.ssh/id_ed25519" }
      // 只被日志的 via 引用；不配 logSources 表示"这台机器本身没有日志源"
    }
  ]
}
```

- `logSources[].name`：该配置内唯一，模型/GUI 用它选条目（**不传路径**）。
- `kind: "file"`：`path` 必须是**绝对路径**；`kind: "journal"`：`unit` 必须是合法 systemd 单元名。
- `via`（可选）：第二跳的 SSH 配置名。不填 = 读**跳板机本机**的文件/journal。
- 相对路径、`..`、通配符、空字符串、重名、`file` 带 `unit`、`journal` 带 `path` 一律在 schema 层拒绝（中文错误）。

### 2.2 模型视角

```text
db_list_ssh_logs()
  → jump-prod（deploy@203.0.113.10:2222）
      app         file    /var/log/app/app.log        应用日志
      app-journal journal app.service                 应用 journal
      mysql-error file    /var/log/mysql/error.log    经 db-host-prod

db_read_ssh_log({ profile: "jump-prod", source: "mysql-error", lines: 100, keyword: "ERROR" })
  → { profile, source, kind: "file", target: "/var/log/mysql/error.log",
      via: "db-host-prod", lines: [...100 行...], lineCount: 100,
      scannedLines: 1200, matched: 100, truncated: false,
      windowBytes: 100000, elapsedMs: 480 }
```

> 额度就是配置里的 `logMaxBytes`（默认 100KB）。装不下时只保留最新（尾部）的行并置 `truncated=true`，模型据此加 `keyword` 或缩小 `lines` 再来一次。

工具描述里明确写：**只能读取配置中已声明的日志源；无法执行命令、无法读取任意文件、无法修改任何内容**。

### 2.3 GUI 视角（**只做配置，不做读取面板**）

**不做「查看日志」按钮/面板**，原因说清楚：

| 对比 | 设置页面板 | 对话中的工具（本计划的主路径） |
|---|---|---|
| 日志去哪了 | 只渲染在设置页，**模型看不到**，人要自己复制粘贴进对话 | 直接进上下文，模型可继续追问、比对代码、定位 |
| 与你说的用途是否一致 | 不一致 | 一致 |
| 成本 | 约 1 人日（RPC + 面板状态 + 渲染用例），且多一个"人也能读日志"的入口需单独做权限/审计论证 | 约 0.5 人日（工具 + 审计） |

**只保留配置入口**：SSH 编辑器新增「日志源白名单」多行文本框（只是表单字段，不是查看器），一行一条：

```text
app | file | /var/log/app/app.log | 应用日志
app-journal | journal | app.service
mysql-error | file | /var/log/mysql/error.log | 经 db-host-prod | via=db-host-prod
```

保存时由 Host 解析 + 校验，错误按行返回（`第 2 行：日志路径必须是绝对路径`）。

> **必须一起修的坑**：`saveSshProfileInto` 是**整体替换**语义，而编辑器不会渲染全部字段。若不做处理，用户在 GUI 里改一次密码就会把 `logSources` 静默清空。计划要求：`body.logSources === undefined` 时**保留**原条目的 `logSources`，显式传 `null`/空数组才清空（并在 CHANGELOG 里写明这条语义）。
>
> 如果评审后认为手工编 JSON 更合适（D3-B），则 GUI 一行代码都不动，但上面这条 merge 保护仍要加。

## 3. 技术方案

### 3.1 为什么能保证"只读"

| 层 | 做法 |
|---|---|
| 输入面 | 模型输入只有 `profile` / `source` / `lines` / `keyword`，**没有路径、没有命令、没有 shell 参数** |
| 传输面 | 文件走 **SFTP**，`sftp.open(path, 'r')` 只读打开；代码中**不实现** `write/append/unlink/rename/mkdir/rmdir/setstat`（不是禁用，是根本没有这些调用点） |
| 命令面 | `journal` 走 `exec` 但**模板固定**：`journalctl --no-pager --output=short-iso -n <N> [-u <unit>] [--since '<t>']`，`unit` 保存时已校验 `^[A-Za-z0-9@._:\-]{1,64}$`，`N` 为整数，`<t>` 仅允许 `-<数字><s\|min\|h\|d>` 或 `YYYY-MM-DD[ HH:MM[:SS]]` 并由 Host 加引号；拼接结果不可能含调用方可控的 shell 元字符 |
| 规模面 | **单次返回 ≤ `logMaxBytes`（默认 100KB）**；行数按字节装得下多少返回多少（内部 2000 行硬顶）；单行 ≤ 2000 字符；总超时 10s |
| 留痕面 | 审计只记 `profile / source / kind / lines / scanned / matched / bytes / 耗时`，**不记正文、不记关键字** |

对比"命令白名单"方案：白名单仍然要经过 shell 拼串，任何一处转义疏漏就是漏洞；本方案把**路径与命令完全排除在调用方输入之外**，注入面为零。这是本设计的核心取舍，评审时请重点看这一条。

### 3.2 新增模块 `src/db/ssh-log.ts`

```ts
export type SshLogKind = 'file' | 'journal'

export interface SshLogSourceSpec {
  name: string
  kind: SshLogKind
  path?: string          // kind=file
  unit?: string          // kind=journal
  label?: string
  via?: string           // 第二跳 SSH 配置名
}

/** 一次读取的结果（工具与 RPC 共用）。 */
export interface SshLogReadResult {
  profile: string; source: string; kind: SshLogKind
  target: string                 // 文件绝对路径 / unit 名（回显用，便于确认读的是哪个源）
  via?: string
  lines: string[]
  lineCount: number
  scannedLines: number           // 窗口内总行数（过滤前）
  matched?: number               // 有 keyword 时的命中数
  truncated: boolean
  windowBytes: number            // 本次读取的窗口字节数（= logMaxBytes）
  elapsedMs: number
  maxBytes: number               // 生效的额度，便于模型判断"能不能再来一次"
}
```

三个可测的纯函数 + 一个 IO 入口：

| 函数 | 职责 | 可单测 |
|---|---|---|
| `tailWindow(buffer, maxLines, maxBytes)` | 从尾部切窗口、按 UTF-8 边界安全解码、处理 CRLF、按行裁剪 | ✅ 纯函数 |
| `filterKeyword(lines, keyword)` | 大小写不敏感子串过滤（≤64 字符） | ✅ 纯函数 |
| `journalArgv(unit, lines, since?)` | 生成固定 argv 并断言无元字符 | ✅ 纯函数 |
| `readLogSource(profile, source, opts)` | 建 SSH（单跳/两跳）→ 取数 → 整形 → 关闭 | 注入 transport 后可测 |

**两跳实现**（`via`）：跳板机上 `forwardOut('127.0.0.1', 0, targetHost, 22)` 拿到 stream，再用 `new Client()` + `connect({ sock: stream, ... })` 在隧道里叠第二层 SSH，然后在其上开 SFTP。**全程仍是纯 SFTP/journal，不借助跳板机上的 `ssh` 命令**。第二跳同样走严格 known_hosts 校验（复用 `verifyHostKeyAgainstKnownHosts`），失败提示复用 `knownHostsFixHint()`。

**连接生命周期**：一次**工具调用** = 为本次涉及的每台目标机建一条 SSH 连接，把该机上所有要读的源读完即关闭（跨源检索不再每源握手），不进 `PoolManager`、跨调用不缓存。日志读取是低频操作，换取"无共享状态、无泄漏面"。见 D8。

### 3.3 配置层改动

- `src/config/schema.ts`：新增 `sshLogSourceSchema`，挂在 `sshProfileSchema.logSources`（`z.array(...).max(20).optional()`）。
  superRefine：重名、`kind` 与 `path`/`unit` 互斥必填、路径绝对化（POSIX `/` 开头且不含 `..`）、`unit` 字符集、`via` 不能指向自己。
- `src/config/mutate.ts`：`saveSshProfileInto` 目前已把 `body.profile` 的未知字段原样带进 `draft` 再 `safeParse`，因此 `logSources` **无需额外分支**即可透传；需补一条用例锁住这一点。
- `src/config/store.ts`：新增 `resolveLogSource(load, profileName, sourceName, workspace?)` → `{ profile, source, error? }`（工作区优先、全局兜底，与连接解析同语义）。
- `src/shared/types.ts`：`SshProfileSpec` 增 `logSources?: SshLogSourceSpec[]`；视图类型增 `logSourceCount` / `logSources`。

### 3.4 工具（模型侧）

| 工具 | 参数 | 行为 |
|---|---|---|
| `db_list_ssh_logs()` | — | 列出当前可见（工作区 ∪ 全局）SSH 配置及其日志源；无凭据；标注 `via`。让模型先知道"这台机器上能读什么" |
| `db_read_ssh_log({ profile, source, lines?, keyword? })` | `lines` 1–2000（默认 200，且受 `logMaxBytes` 额度约束）；`keyword` ≤64 字符 | 解析 → 建连 → 读窗口 → 过滤 → 整形 → 审计 → 返回 |
| `db_search_ssh_logs({ keyword, profile?, sources?, contextLines? })` | `keyword` 必填（≤64 字符）；`sources` 省略 = 该配置下**全部**源；`profile` 省略 = 所有含源的配置；`contextLines` 0–10（默认 2） | **跨源检索**：一次调用遍历多个白名单源，各自取尾部窗口后本地匹配，按源聚合返回「源 → 命中行 + 上下文」。用于"拿到关键词（traceId/错误码/接口名）后去别的日志里对一遍"。总量统一受 `logMaxBytes` 额度收口 |
| `db_add_ssh_log_source({ profile, name, kind, path?, unit?, label?, via?, delete? })` | **已确认纳入**：对话里直接登记/删除一个日志源（对齐 v0.14 `db_add_connection` 的"一句话加库"体验） | 只改该 SSH 配置的 `logSources` 数组；不碰凭据与其它字段；先全量校验再落盘；审计 |

工具描述里明确写清用途与边界（中文）：**用于在对话中读取服务器日志以定位代码/接口问题；只能读取配置中已声明的日志源，无法执行命令、无法读取任意文件、无法修改任何内容**。

**排查工作流（工具描述里给模型的操作顺序建议）**：

```text
1) db_list_ssh_logs                          → 看这台机器登记了哪些源
2) db_read_ssh_log(source=app, lines=200)     → 看到报错，例如 "traceId=8f3a… status=500"
3) db_search_ssh_logs(keyword="8f3a", contextLines=3)
                                              → 同一 traceId 在 nginx/gateway/db 日志里的前后文
4) （可选）db_query 查库里的对应记录，db_describe_table 核对字段
```

> 设计取舍：跨源检索**仍然只读尾部窗口**（不做全文件扫描、不发 `grep`），所以命中的是"最近数据"；`truncated` + `scannedBytes` 会把窗口边界明确回显，避免模型误以为"没命中=不存在"。

错误分类复用既有 `DbErrorKind`：

| 场景 | kind | 文案要点 |
|---|---|---|
| 配置/源不存在 | `config` | 列出可用配置与源名 |
| 路径不在白名单 | `config` | 不可能发生（无路径入参），仅防御性保留 |
| SFTP 被禁 | `config` | 「服务器未开启 sftp 子系统」+ 建议改用 `journal` 或联系运维 |
| 文件不存在 / 无读权限 | `permission` | 指明路径与「该账号是否可读」 |
| journalctl 不存在 | `config` | 「目标机没有 journalctl（非 systemd 或容器精简镜像）」 |
| 握手/主机密钥 | `config` | 复用现有 `knownHostsFixHint()` 多行可执行提示 |
| 超时 | `timeout` | 提示缩小 `lines` 或检查网络 |

### 3.5 RPC（GUI 侧）

| 方法 | 入参 | 出参 |
|---|---|---|
| `sshProfiles.save`（扩展） | `+ logSources?: [...]`；`undefined` = 保留原值，`[]`/`null` = 清空 | 不变 |
| `connections.list` / `workspaces.list`（扩展） | — | sshProfiles 视图增 `logSourceCount`（只给计数，不返回内容） |

**不新增 `sshLogs.read` / `sshLogs.list`**：没有读取面板，就没有 GUI 侧的读通道（少一条出口就少一处要论证的权限面）。`workspace` 语义对 `sshProfiles.save` 沿用既有 fail-closed 白名单（`resolveKnownWorkspace`），出口复用 `sanitize()`，审计 `channel='rpc'`。

### 3.6 插件配置项（`src/index.ts` `Config`）

| 项 | 默认 | 说明 |
|---|---|---|
| `logEnabled` | `true` | 总开关；`false` 时不注册日志工具 |
| `logMaxBytes` | `100000` | **单次返回的日志额度（字节）**，默认 100KB；设置页一个数字输入框 |
| `logTimeoutMs` | `10000` | 单次读取总超时 |

> 只有这三个配置项。行数不单独设上限：额度按字节算，能装多少行就返回多少行（内部另有 2000 行硬顶，防止极短行撑爆条目数，不可配）。白名单为空 = 没有能力，所以不需要"按机器开关"；`logEnabled` 只用于全局急停。

### 3.7 输出额度：一个数字

**不做动态预算**。（曾设计过读 `contextPressure` 按比例算额度，评审时否掉：十几处配置 + 隐私/版本依赖 + 一堆边界用例，收益与复杂度不成正比。）

只有一个配置项 `logMaxBytes`，默认 **100KB**，对应设置页一个数字输入框：

```text
本次可返回字节 = logMaxBytes（默认 100000）
行数           = 按字节装得下多少行（内部另有 2000 行硬顶，不可配）
超额           = 只保留最新（尾部）的行，返回 truncated=true + maxBytes
```

- **为什么 100K**：约 3.3 万字 / 2.5 万 token 上下，占一次正常上下文不到 1/4，排查一段报错通常够用。
- **放哪儿**：插件配置（`Config`），DSH 设置页的插件配置表单直接渲染成输入框，全局生效；不按日志源单独配。
- **超了怎么办**：模型看到 `truncated=true` 和 `maxBytes`，自行加 `keyword` 或指定更小的 `lines` 再来一次——两三次往返比一次塞满更可控。
- **要调就改这个数字**；确实需要"跟随上下文"再单独立项，不在本期。

| 编号 | 问题 | 方案 A（推荐） | 方案 B | 影响 |
|---|---|---|---|---|

## 8. 风险与应对

| # | 风险 | 应对 |
|---|---|---|
| 1 | **SFTP 服务端 fixture 成本高**（ssh2 服务端 SFTP 是低层事件协议，需手写 handle/status 应答） | 先做 §7.1 纯函数 + 注入式 transport 假实现（覆盖 90% 逻辑）；E2E 若超 0.5 人日则改为**真实服务器人工验证并写入 CHANGELOG 的「运行验证」**，同时保留 fixture 待办 |
| 2 | 目标服务器禁用 sftp 子系统 | 明确报错 + 建议用 `journal` 源；不做"退化成 exec tail"（那会重开命令面） |
| 3 | 两跳的 known_hosts 记录缺失（很常见） | 复用既有严格校验与可粘贴提示；文档写明"两台机器各需一次登录" |
| 4 | 日志轮转：读到的是旧 inode / 半行 | 只读尾部窗口；半行丢弃并置 `truncated=false` 但 `partialLine` 标记（v1 用 `truncated` 语义说明），文档记为边界 |
| 5 | 日志含密码/token，返回即进对话 | 单次额度 100KB 可调（§3.7）；工具描述与文档双重提示；`logEnabled` 可急停；D6 可加脱敏 |
| 6 | `journalctl` 权限（非 `systemd-journal` 组） | `permission` 分类 + hint 说明加组方法（只提示，不执行） |
| 7 | 读取大文件阻塞事件循环 | 窗口上限 + 流式读取 + 10s 超时；禁止整文件读入（`.gz` 除外，见 D5） |
| 8 | 100KB 额度对"日志很长 + 需要上下文"不够 | 模型可加 `keyword` 缩小范围，或用户调大 `logMaxBytes`；真需要动态额度再单独立项 |

**适用范围**: 本仓库全部代码、测试与文档工作。任何会话（人工或 AI）生成本项目代码/文档前，先遵循本规范。

## 1. 技术栈与运行环境

| 项 | 约定 |
|----|------|
| 语言 | TypeScript 5（strict），ESM（`"type": "module"`） |
| 运行时 | Node.js ≥ 22（v0.11 起，`node:sqlite` 要求；`package.json#engines` 为准） |
| 构建 | `tsup` 双条目：Host 半区 `src/index.ts` → `lib/index.js`（esm + dts）；Client 半区 `src/client/main.ts` → `lib/client.js`（cjs + `__ModuleLoader__` banner/footer，externals 仅 react/react-dom） |
| 依赖原则 | 运行依赖只允许 `mysql2` / `pg` / `zod` / `node-sql-parser` / `ssh2`（v0.16 起，用于 FR-13 SSH 隧道）；`@deepseek-ai/*` 一律 peerDependencies（range 带显式预发布分支）；禁止引入 native binding 依赖（SQLite 走 `node:sqlite`）。`ssh2` 自身为纯 JS 实现，其 `cpu-features` + `nan` 是**可选**加速依赖——缺失时 ssh2 仍正常工作，安装失败不会中断 `npm install`（已验证：引入 ssh2 未带来 node-gyp/prebuild 工具链） |
| 目标宿主 | DSH ≥ 0.2.1-alpha.2（**只跟随 0.2.1 线**；0.1.x 与 0.2.0 不再声明，理由见 README「兼容性：支持的 DSH 版本」）；Config 用 `@deepseek-ai/schemastery`（无 `.optional()`，属性默认可省略），业务校验用 zod v4 |

## 2. 工程结构与模块职责

- `src/index.ts` 是唯一 Host 入口；插件停止时必须完整回收注册与连接池（`ctx.effect` cleanup）。
- **方言收敛**：一切数据库差异收敛到 `src/db/dialect.ts` 接口与三个 driver 文件；工具/RPC/GUI 代码**不得出现** `if (spec.dialect === …)` 形式的业务分支（GUI 仅允许徽章/表单字段切换）。
- 新增数据面能力 = `src/db/*`（driver/metadata）+ `src/tools/*`（工具）+ `src/rpc/routes.ts`（如 GUI 需要）+ `src/client/*`（如 UI 需要）+ 测试。
- 全部跨模块类型放 `src/shared/types.ts`；结果集截断统一走 `src/shared/truncate.ts`。
- `bin/encrypt.js` 仅做密文生成 CLI，不承载业务逻辑。

## 3. 编码规范

- 命名：文件 kebab-case（`mysql-driver.ts`）；类型 PascalCase；函数/变量 camelCase；常量大写蛇形。
- 错误与文案：**面向用户的错误信息、工具描述、GUI 文案一律中文**；错误信息必须可读且不含凭据片段（脱敏后再抛出，参见 `src/secrets.ts` 静态文案先例）。
- 注释：复杂安全逻辑（分类、令牌、沙箱、指纹）必须写"为什么"，引用审计编号（H1/N2 等）便于回溯。
- 导出：纯函数优先（如 `shouldBackup`、`enforceReadLimit`、`planRowBackup`），便于矩阵测试；副作用集中在 tools 层。

## 4. 安全红线（强制，违反即返工）

1. **密码**：配置中只允许 `$ENV:VAR` 引用或 `enc:v1:` AES-256-GCM 密文；明文在 zod schema 层拒绝；任何出口（工具返回/RPC/日志/错误文案/GUI）不得出现明文密码、完整连接串或值片段；GUI 编辑不回显。
2. **SQL 安全网关**：两条通道一次只接受一条语句；`multipleStatements: false`、`localInfile: false` 必须钉死；解析失败按最高危处理；只读白名单之外一律拒绝；`EXPLAIN` 内层、`INTO OUTFILE`、`USE/SET` 保持拦截；规范化文本必须复核往返一致（类别翻转/危险标记消失即拒绝）。
   - **执行文本必须是调用方原文**：解析器重新序列化的产物（`node-sql-parser` 的 `sqlify`）**只能用于往返复核**，绝不可作为执行语句或确认令牌的绑定文本。该库的 `type` 参数对标识符引用无效——即使传 `type: 'postgresql'` 也会输出 MySQL 反引号，PostgreSQL 直接报 `syntax error at or near "\`"`（v0.14.1 修复的真实故障：所有可解析的 PG 查询全废）。复核期间采用更严格判定时，**只继承判定（`dangerous`/`reason`），不继承文本**。
3. **高危确认**：DROP/TRUNCATE/ALTER/RENAME、无 WHERE 的 UPDATE/DELETE 必须先拒绝；宿主审批服务可用时优先人工审批（用户拒绝不得签发令牌）；不可用时退回 HMAC 确认令牌（一次性、5 分钟、绑定连接+语句哈希、常量时间比较）。
4. **extraParams**：denylist 键（`uri`/`connectionString`/`multipleStatements`/`ssl`/`localInfile` 等）在 schema 拒绝 + 驱动侧防御性剥离双层保留；连接身份/池策略/TLS 字段必须后置展开（永不可被覆盖）。
5. **SQLite 路径沙箱**：`validateSqliteFilePath` 每次 acquire 必须重跑（fail-closed）+ realpath 解析 + `root + path.sep` 防前缀攻击；不得放宽为"仅建池时校验"。
6. **池缓存**：键必须含连接规格指纹（host/port/username/password/file/ssl/extraParams 的 sha256）；close/retainOnly 按连接名精确归因，禁止 `::` 字符串前缀拼接。
7. **审计**：新工具/新 RPC 出口必须接入审计 wrapper；语句写入前必须过 `sanitizeSql`；审计文件不含结果数据。
8. **测试夹具**：测试中不得出现真实主机、真实密码；一律 `$ENV:` 形态或 `p@ssw0rd` 类假值 + 临时密钥文件。

> 每次涉及安全面的变更，合并前自查 §8.1 安全基线清单（见需求设计文档）；大规模改动后应主动发起一轮安全复查并产出到 `docs/records/`。

## 5. 测试与验证规范

### 5.1 验证矩阵（提交前必须全绿）

| 验证层 | 命令 | 说明 |
|--------|------|------|
| 类型检查 | `node node_modules/typescript/bin/tsc --noEmit` | 全部 src + tests |
| vitest 全套 | `node --import ./scripts/register-vitest-shim.mjs scripts/run-vitest.mjs` | 11 spec；沙箱内经 vitest shim 运行 |
| 核心逻辑 | `node scripts/verify.mjs` | 依赖 `.build/`（先 `tsc --outDir .build --module nodenext --moduleResolution nodenext --target es2022 --esModuleInterop --skipLibCheck --noEmit false --declaration false`），node:test 跑核心安全函数 |
| MySQL 集成（可选） | `DBM_TEST_URL=mysql://user:pass@host:3306 npm run verify` | 需真实 MySQL；套件自建/自毁临时库；本机执行 |

### 5.2 沙箱限制（重要）

DSH 沙箱禁止 esbuild spawn 子进程（`spawn EPERM`），因此：

- `npm run verify` / `npm test`（vitest 直跑）**在沙箱内不可用**，必须使用上表 shim runner。
- `npm run build`（tsup → esbuild）**在沙箱内同样不可用**，且失败是**静默的**（进程退出码可能为 0 或报 Access denied，产物不更新）——改完源码刷新页面看不到新功能时，优先怀疑「构建没跑成」。沙箱内请用 `node scripts/build-sandbox.mjs`（纯 TypeScript API 编译，不 spawn）生成 `lib/`：host 半区输出为多文件 ESM（行为与 tsup 等价，`package.json#files` 已含整个 `lib` 目录，发布不受影响）；client 半区仍是单文件 CJS + ModuleLoader wrapper。
- `scripts/` 下五个文件（vitest-shim / vitest-loader / register-vitest-shim / run-vitest / build-sandbox）是为此搭建的沙箱基础设施，修改需谨慎并保证 `.not`/`.toThrow(Class)`/`.toBeInstanceOf`/`.rejects` 等 matcher 兼容。

### 5.3 测试要求

- 新功能/修复必须带测试；安全修复必须补回归用例（引用审计编号）。
- spec 命名 `tests/<主题>.spec.ts`；集成测试放 `tests/integration/` 并以 `DBM_TEST_URL` 门控。
- 涉及三方言的行为必须给出方言矩阵用例（参考 `tests/hardening.spec.ts`）。

## 6. 变更与文档规范（含变更日志强制规则）

### 6.1 【强制】变更日志规则

**先判断变更类型，再决定要不要建 CHANGELOG 文件**：

| 变更类型 | 判据 | PROJECT 索引行 | CHANGELOG 文件 |
|---|---|---|---|
| **代码 / 发版** | `src/`、`tests/`、`bin/`、`scripts/`、`package.json`、`cordis.patch*.yml` 任一有改动，或发布新版本 | 必须 | **必须** |
| **纯文档 / 流程** | 只改 `README.md`、`AGENTS.md`、`THIRD-PARTY-NOTICES.md`、`docs/*.md`（含本规范自身、PROJECT、发布指南） | 必须 | **不建**——变更说明就写在索引行的「一句话说明」里，详情链接填 `本提交说明` |

**代码 / 发版变更**必须完成以下两步，缺一不可：

1. **更新 [docs/PROJECT.md](PROJECT.md) 的「变更日志索引」表**：在表**末尾追加一行**——`# | 版本区间 | 日期 | 主题 | 类型 | 一句话说明 | 详情链接`；`#` 取上一行序号 +1（只增、不重排、不复用），整表保持按 `日期` 正序、同一天按登记先后，因此新行天然落在末尾，无需手工插行。
2. **新建或更新 `docs/CHANGELOG-<版本或区间>-<主题>.md`**：承载该次变更的全部细节。

**CHANGELOG 文件命名**：只允许两种——`CHANGELOG-v<X>-<主题>.md`（单版本，如 `CHANGELOG-v0.12-安全加固.md`）或 `CHANGELOG-v<A>-v<B>.md`（区间合并，如 `CHANGELOG-v0.7-v0.11.md`）。**文件名必须以版本号开头**：`CHANGELOG-流程-…`、`CHANGELOG-文档-…` 这类非版本前缀一律不允许（流程 / 文档变更按上表不建文件）。

**CHANGELOG 文件结构模板**：


## 7. Git 与发布规范

### 7.1 分支与提交

- 分支：`master`；远程：`origin-gitee`（https://gitee.com/<account>/dsh-db-manager.git），推送 `git push origin-gitee master`。
- 提交信息：Conventional Commits + 中文描述（`feat: …` / `fix: …` / `security: …` / `docs: …` / `chore: …`），正文说明动机与要点。
- 提交前：确认 §5.1 验证矩阵全绿；确认 `node_modules/`、`lib/`、`.build/`、`dist/`、`.env*` 等未被暂存（`.gitignore` 已覆盖）。

### 7.2 版本标签与 Release（【强制】按 DSH 版本可追溯）

DSH 换代很快，不同 DSH 版本需要不同的插件版本。**只要「DSH 兼容性」发生变化（新增或收窄 `dsh.engines.dsh` 区间，或在新 DSH 版本上完成实测），就必须发版、打 tag、建 Release**——否则用户无法按自己正在用的 DSH 版本装到对应插件。

1. **版本号先行**：先 bump `package.json#version`（仅修 bug = patch；能力新增或兼容区间变化 = minor；配置/协议不兼容 = major），并让 `dsh.compatibility.dshReleases` 与**实际实测过**的 DSH 版本完全一致。
2. **打 tag**：`git tag -a v<version> -m "dsh-db-manager v<version> (DSH 实测 <ver>)"`；tag 名必须与 `package.json#version` 严格一致（`v0.22.0` ↔ `0.22.0`）。**只给实测通过的版本打 stable tag**；没实测的版本不许打 tag，也不许写进 `engines` / `dshReleases`。
3. **建 Release**（GitHub 与 Gitee 都建，标题用 `v<version>`），正文至少包含：
   - **支持的 DSH 版本**：声明区间 + 实测版本，例：`^0.2.1-alpha.2`（实测 `0.2.1-alpha.2`、`0.2.1-rc.2`）；
   - **两种安装方式**：`dsh plugin --profile <name> add dsh-db-manager@<version>`；或 `git clone` → `git checkout v<version>` → `npm install && npm run build` → `dsh plugin --profile <name> add .`；
   - **主要变更**（链接对应 `docs/CHANGELOG-*.md`）；
   - **升级影响**（配置格式 / 工具协议是否兼容上一版本）。
4. **tag 就是安装契约**：用户按 tag 安装，等于锁定「声明支持其 DSH 版本」的那一版；因此**已发布的 tag 不得移动、不得重写历史**——需要修正就发新的 patch 版本。
5. 面向 alpha / rc 的预发布版本如需打 tag，使用带后缀的版本号并在 Release 上勾选 pre-release，不得占用 stable 号段。

### 7.3 发布到插件市场

严格按 [docs/发布指南-插件市场.md](发布指南-插件市场.md) 执行：仓库推送 → 打 tag 并建 Release（见 §7.2）→ `npm publish`（或源码方式）→ awesome-dsh-plugin 目录 PR。

```bash

npm run build               # tsup 双条目构建 → lib/（沙箱内不可用，见 §5.2）
node scripts/build-sandbox.mjs   # 沙箱内构建 lib/（纯 TypeScript API，不 spawn）
node node_modules/typescript/bin/tsc --noEmit          # 类型检查

DBM_TEST_URL=… npm run verify   # 真库集成测试（本机）
node <插件目录>/bin/encrypt.js  # 生成 enc:v1 密文（人工终端执行）
```

## 一、新发现（含修复状态）

### N1｜【中·偏高】【已修复】extraParams 白名单可被 mysql2 的 `uri` 参数整体绕过
- **位置**: `src/config/schema.ts`（FORBIDDEN_EXTRA_PARAMS + extraParamsSchema）、`src/db/mysql-driver.ts`（toMysqlOptions）
- **机理**: M6 修复只对 extraParams 的**字面 key** 做 denylist。mysql2 `ConnectionConfig` 在构造时若发现 `options.uri`，会把 URI **query string 逐 key 合并**（`node_modules/mysql2/lib/connection_config.js:80-87`：`if (options[key]) continue; options[key] = uriOptions[key]`，query 值先尝试 JSON.parse）。凡插件未显式预置的选项都会被 URI 注入——而 `multipleStatements`、`localInfile`、`ssl`（spec.ssl 关闭时整个键不存在）、`socketPath`、`authSwitchHandler`、`infileStreamFactory` 恰好都未预置。
- **PoC**: 连接配置 `extraParams: { "uri": "mysql://a:b@h/db?multipleStatements=true&localInfile=true&ssl={\"rejectUnauthorized\":false}" }` —— schema 校验通过，驱动侧 multipleStatements/localInfile 被打开、TLS 校验被关。注意即使把 `multipleStatements: false` 预置进 PoolOptions 也防不住（`false` 为 falsy，仍会被 URI 值覆盖），**唯一可靠修复是 denylist 掉 `uri`/`connectionstring` 键并在 spread 后防御性剥离**。
- **可达性**: 工作区配置文件（仓库自带 `.dsh/db-manager.json`，M4 已有 shadowing 警告但仅是提示）、GUI 保存、或用户手改全局配置。结合工作区劫持时攻击者本可直接改 host，故单列"绕过安全加固机制"而非独立利用链；但对"用户以为受 M6 保护"的全局连接是实打实的降级面（multipleStatements 一旦为真，"单语句强制 + multipleStatements 关闭"的双保险只剩解析器一层）。
- **修复实施**: ① schema denylist 补 `uri`/`connectionstring`（refine 已按小写比较，大小写变体同锁）；② `toMysqlOptions` spread 后防御性 `delete uri/connectionString`，并硬性钉死 `multipleStatements: false`、`localInfile: false`；③ pg 侧 denylist 补 `uri`、`toPgConfig` 同样防御性剥离。测试：config.spec（URI 四形态拒绝）+ hardening.spec（`buildMysqlPoolOptions` 断言剥离与钉死）。

### N2｜【中】【已修复】连接池缓存键不含连接规格，改配置后旧池失效不清理（陈旧目标/陈旧凭据）
- **位置**: `src/db/pool.ts`（旧 key = `name::dialect::db`；retainOnly 只按"名字消失"清理）、`src/tools/metadata.ts`（openPoolFor 每次重新解析 spec 但 acquire 命中旧驱动）
- **机理**: 编辑既有连接的 host/port/username/password/ssl/file 后（GUI 保存或手改配置），连接名不变 → 缓存命中返回**旧 spec 建的驱动**，工具仍连旧库/用旧凭据；`db_reload_config` 的 retainOnly 也不会清它。GUI「测试」走 `probeConnection`（全新连接）测的是新配置 → 出现"测试通过但查询仍打到旧库"的误导组合。
- **危害方向**: 用户"改指向新库"的意图被静默吞掉（数据继续落旧库）；泄露后改密码不生效；把连接改到隔离环境后查询仍打生产。
- **修复实施**: 池缓存重构为「连接名 → 内层缓存」两级 Map，内层键携带 spec **指纹**（host/port/username/password/file/ssl/extraParams 的 sha256 前 12 位）。指纹变化 → 建新驱动并关闭旧驱动；`db_reload_config`/保存均无需额外逻辑。测试：unchanged spec 复用同一驱动；改 host 后新驱动创建且旧驱动 `end()` 被调用、后续 acquire 稳定。

### N3｜【中】【已修复】SQLite 路径沙箱只在建池时校验：跨工作区缓存命中可绕过 allowedRoots；symlink 可指向根外
- **位置**: `src/db/sqlite-driver.ts`（校验在 create 内）、`src/db/pool.ts`（缓存键用原始 `spec.file`）、`src/tools/metadata.ts`（allowedRoots=[session.cwd]）、`src/tools/index.ts`（测试路径 root=process.cwd()）
- **机理**: 池/驱动为**进程级共享**。工作区 A 打开过 `file: ./data.db` 的连接后，工作区 B 对同名同 file 的连接调用工具时，`validateSqliteFilePath`（本应以 B 的 root 拒绝）因缓存命中**根本不执行**，B 直接拿到 A 解析出的驱动句柄；反之 A 的合法句柄也会泄露给 B。另：`path.resolve` 不解析 junction/symlink，工作区内植入链接可让"路径在根内、真实目标在外"。
- **附带说明**: `path.resolve` 以进程 cwd 为基准导致的"工作区相对路径"错位是 fail-closed 行为（与 GUI 提示不符但无安全风险），本轮未改语义；`db_test_connection`/RPC 测试用 process.cwd() 兜底为 v0.9 H2 既有设计，维持并记录。
- **修复实施**: ① `acquire` 对 **sqlite 每次 acquire 都重跑** `validateSqliteFilePath`（fail-closed，空 allowedRoots 一律拒绝）；② sqlite 缓存键使用 **realpath 解析后的文件路径**，两工作区相对字符串相同也不会共享句柄，且连接内其它 sqlite 旧目标条目会被清理；③ `validateSqliteFilePath` 用 `fs.realpathSync` 解析文件（不存在时回退最近存在祖先目录）与 allowedRoots 后再做包含性判断。测试：缓存命中后换 root 必拒；根内 symlink→根外文件必拒（无 symlink 权限环境自动跳过）；根内普通文件返回 realpath。

### N4｜【中】【已修复】MySQL 通道 queryTimeoutMs 完全未生效，且大 LIMIT 全量缓冲
- **位置**: `src/db/mysql-driver.ts`（create 丢弃 queryTimeoutMs）、`src/tools/data.ts`（pool.run 不传 timeout）、`src/shared/truncate.ts`（截断发生在**全量取回之后**）
- **机理**: v0.7 驱动抽象重构后 mysql 通道根本不带 timeout（PG 靠 statement_timeout 有 15s，SQLite 同步调用不受影响）。`SELECT * FROM t LIMIT 99999999999`（自带 LIMIT → 不注入上限）会把全表拉进宿主内存再截断，叠加无超时 → 卡满工具超时 + 服务器继续跑 + 宿主 OOM 风险。
- **修复实施**: ① `MysqlDriver` 保存 `queryTimeoutMs`，query/execute/withTransaction 全部默认下发 `timeout: timeoutMs ?? this.queryTimeoutMs`（mysql2 超时是客户端不活动超时、不终止服务器端执行——M7 语义照旧，但宿主不再无限等待）；② 新增导出 `enforceReadLimit(statement, limit, cap)`：语句自带 LIMIT 超过请求 cap 时用派生表包裹 `SELECT * FROM (…) AS __dbm_l LIMIT cap`，外层 LIMIT 真正限制驱动缓冲的行数（原 LIMIT 保留在派生表内）。测试：`enforceReadLimit` 4 例（无 LIMIT 追加 / 超限包裹 / 小 LIMIT 与 NaN 不动 / 尾分号剥离）。

## 三、复查确认仍然成立的安全设计（抽样复验）

- 只读通道：白名单 kind + INTO/EXPLAIN-内层/USE/SET 拦截 + 单语句强制 + 注释感知的 LIMIT 注入（含包裹式兜底）+ 规范化复核（N10）——未发现可达绕过；多语句夹带维持"解析器单语句 + multipleStatements 钉死（N1 后更硬）"双保险。
- 确认闭环：HMAC-SHA256 绑定连接名+语句 SHA256+过期、timingSafeEqual、5 分钟 TTL、一次性台账（同步消费无 TOCTOU）、人类显式拒绝时不发令牌。
- 密钥处理：AES-256-GCM + 随机 IV、密钥损坏拒绝静默轮换（运行时 + CLI 两侧同语义）、明文 schema 拒绝、错误文案不回显明文片段、RPC/审计出口统一脱敏。
- 标识符注入：`quoteIdentifier` 全字符集白名单，PRAGMA/SHOW CREATE/DROP 备份清理路径均过校验；备份四段 SQL 执行前逐一重分类（kind 校验）。
- GUI/RPC：React 全 children 渲染无 dangerouslySetInnerHTML、令牌仅注入页面、body 1MB 上限、原子写配置、损坏文件拒改写（M5）、令牌常量时间比较（N7）。

## 五、残余风险（记录在案，非本轮未修事项）

1. **审计含语句字面量**（N8 残余）：`UPDATE … SET token='…'` 等数据面字面量会进审计文件（≤2000 字符）；如需更强隐私可加长度阈值前的 VALUES 检测或干脆只存语句形状。
2. **只读通道不承诺无副作用**（N10 残余）：SELECT 调用带写副作用的存储函数/UDF 无法静态识别，且被截断触发的 COUNT 估算会二次执行该语句；根本缓解是 DB 侧最小权限账号（PRD 既有建议）。
3. **SQLite 测试路径 process.cwd() 兜底**：v0.9 H2 既有设计（CHANGELOG §2.1 已注明），维持现状。
4. **确认令牌非真人间隔**：v0.9 审计既有记录（审批通道不可用时退回令牌闭环），维持现状。

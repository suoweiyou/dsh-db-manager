# dsh-db-manager 代码安全审计报告

**范围**: `src/**`（Host 全部 + Client）、`bin/encrypt.js`、`tsup.config.ts`、`tests/**`，对照 `docs/PRD-dsh-db-manager-数据库管理插件.md`（v0.4）的 G1–G6 安全基线
**方法**: 全量通读源码 + 用项目实际安装的 node-sql-parser v5 对真实 `classifySql` 跑边界用例实证 + 核实宿主 webserver 注入渲染与 mysql2 超时实现

---

## 一、结论总览

整体安全设计质量较高：密码"明文禁止/加密/环境变量"三态强制、出口统一脱敏、多语句双通道拒绝、USE/SET/INTO 类全拦截、confirmToken HMAC 绑定+一次性、工具与 RPC 出参无凭据。**未发现"任意人可读写数据库"级别的可直接利用漏洞**，但存在 1 个读通道写执行绕过、1 个设计级控制力缺陷，以及若干中低危问题。

| 级别 | 编号 | 问题 |
|------|------|------|
| 高 | H1 | `EXPLAIN ANALYZE <写语句>` 可经只读通道 db_query 原样执行 |
| 高 | H2 | 确认闭环不具人工强制力：拒绝即自动回传新 confirmToken（PRD 风险#2 已接受，仍列为最高设计风险） |
| 中 | M1 | INSERT/REPLACE 一律判"高危"，每次写都进确认闭环，与工具描述/PRD 不符 |
| 中 | M2 | 明文误用时密码前 12 字符泄漏到对话/日志 |
| 中 | M3 | 审计日志可存 SQL 内嵌明文口令（如 `IDENTIFIED BY '...'`） |
| 中 | M4 | 工作区 `.dsh/db-manager.json` 零信任自动加载 + 同名静默覆盖全局连接 |
| 中 | M5 | 全局配置解析失败时 GUI 保存会整体覆写，静默丢全部连接 |
| 中 | M6 | `extraParams` 可覆盖 mysql2 安全相关驱动选项（multipleStatements/ssl 等） |
| 中 | M7 | mysql2 查询超时是客户端假超时，不终止服务器端执行 |
| 低 | L1–L11 | 见 §四 |

## 二、高危

### H1 只读通道可执行 `EXPLAIN ANALYZE <写语句>`（实证）

**位置**: `src/safety/classify.ts:48`（EXPLAIN 属 READ_TYPES）、`classify.ts:163-190`（兜底 regexClassify）、`src/tools/data.ts:87-92`（db_query 只查 kind/dangerous，不查 reliable）

**实证结果**（真实代码运行）:

```
[explain-analyze-delete] reliable=false kind=read dangerous=false limit=-（limit=undefined → 不注入 LIMIT）
[explain-analyze-delete] statements[0].statement = "EXPLAIN ANALYZE DELETE FROM t"   ← 原样透传执行
```

node-sql-parser（v5，mysql 方言）对 `EXPLAIN DELETE/UPDATE`、`EXPLAIN ANALYZE …` 全部解析失败 → 落入正则兜底 → 动词 EXPLAIN 命中 READ_VERBS → 判为 `read` 且 `dangerous=false`。db_query 的门禁只检查 `kind==='read' && !dangerous`，于是语句**原文**直接发给服务器。

**影响**:
- **MariaDB**（mysql2 可直连，插件未阻止）：EXPLAIN ANALYZE 支持 UPDATE/DELETE/INSERT 并**实际执行**内层语句 → 完整的"只读通道执行写语句"绕过，只读模式承诺（G6：只读下写 100% 拒绝）被打破。
- **MySQL 8.0**：`EXPLAIN ANALYZE` 目前面向 SELECT，写语句形态会报错，暂无实际写；但 `EXPLAIN UPDATE/DELETE`（无 ANALYZE，显示执行计划不执行）当前是"靠 MySQL 语义保证安全"，网关自身无检查。MySQL 未来版本扩展 ANALYZE 支持面时此洞即变成现实。

**修复建议**:
1. AST 层：对 `explain` 类型节点检查内层 `node.stmt.type`，非 read 内层一律 refuse（db_query 拒绝、db_execute 按 write/ddl 走）。
2. 兜底层：`regexClassify` 剥掉 `EXPLAIN` 前缀后对内层动词分类；EXPLAIN + 非 SELECT/SHOW 内层动词 → `unknown/dangerous`。
3. 回归用例加入 `EXPLAIN ANALYZE DELETE FROM t`、`EXPLAIN UPDATE …`。

### H2 确认闭环不构成人工控制（设计级，PRD 风险#2 已知）

**位置**: `src/tools/data.ts:239-246`（校验失败 → `issueConfirmToken` 立即随拒绝结果回传给模型）

拒绝响应自动附带新签发的有效 confirmToken。模型**无需任何真实用户确认**，带 token 重试一次即可执行 DROP/TRUNCATE/无 WHERE 的 UPDATE 等任意高危语句。令牌防的是"换语句重放/伪造"，防不了"未经确认直接用"。PRD §6.4 注与风险#2 已明示接受（token + 审计 + 工具描述约束），但这是整个 G5 的实际安全上限：**闭环强度 = 模型自觉**，注入/越权的模型可一键过闸。

**修复建议**（按强度递增）:
1. 接入宿主审批栈（node_modules 已有 `@deepseek-ai/dsh-user-approval`）对 `db_execute` 高危调用强制人工确认；
2. refusal 不回传 token——token 改由用户显式动作产生（GUI 粘贴/对话中人工下发），模型侧永远拿不到"自动续期"；
3. 至少：审计增加"自签自用"特征（issue→use 间隔 < 1s 且无用户轮次）供事后追溯。

## 三、中危

### M1 INSERT/REPLACE 全部被误判"高危"（实证）

**位置**: `src/safety/classify.ts:231` — `dangerousBase = … || (kind === 'write' && !hasWhere)`

INSERT/REPLACE 天然无 WHERE → 每条普通 INSERT 都 `dangerous=true` → 必走确认闭环。实证：`INSERT INTO t VALUES (1)` → `kind=write dangerous=true`。

**影响**: 与 `db_execute` 工具描述（"UPDATE/DELETE without WHERE"才高危）、PRD FR-9/§6.4（非高危写直接执行）不符；更重要的是确认噪音会让模型/用户机械地带 token 重试，**实质性训练并弱化整个确认机制**（与 H2 叠加）。

**修复**: WHERE 缺失规则仅适用于 UPDATE/DELETE（`kind==='write' && (nodeType==='update'||nodeType==='delete') && !hasWhere`），并补测试。

### M2 明文密码误用时前 12 字符泄漏

**位置**: `src/secrets.ts:43` — `非法的密码环境变量引用「${raw.slice(0, 12)}…」`

该消息经 `describePasswordIssue`（`db_list_connections` 的 `issue` 字段、GUI 警告条）与 `db_test_connection`/`db_query` 的 failureMessage、审计 `detail` 进入模型上下文与日志。触发条件是用户把明文写进 password 字段（本就是策略违规场景），但此时**密码前 12 字符进入对话与磁盘日志**，违反 G6"0 处明文"。

**修复**: 报错改为静态文案 + 仅报长度/形态（如「密码字段不允许明文（长度 N）」），不回显任何值片段。

### M3 审计日志可落 SQL 内嵌明文口令

**位置**: `src/audit/log.ts:36-42`（sanitizeSql 只打码 `$ENV:`/`enc:v1:` 引用形态）

`db_execute` 全量 SQL（≤2000 字符）写入 `~/.dsh/db-manager/audit/*.jsonl`。`CREATE USER 'u' IDENTIFIED BY '明文'`、`ALTER USER … SET PASSWORD`、含密码字面量的 INSERT/UPDATE 都会把明文写进审计文件——与 FR-11"不含凭据"承诺冲突。

**修复**: sanitizeSql 增加 `IDENTIFIED (WITH … )? BY\s+'[^']*'`、`PASSWORD\('[^']*'\)` 等形态打码；或在文档明示该边界。

### M4 工作区配置零信任 + 同名静默覆盖

**位置**: `src/tools/workspace.ts`（cwd 自动取会话）、`src/config/store.ts:19-22, 82-104`

会话 cwd 下的 `.dsh/db-manager.json` 被自动加载且**同名连接静默覆盖全局**。克隆含恶意该文件的仓库后：AI 按用户指令调用 `db_query`/`db_test_connection` 即向攻击者主机发起连接；若其 password 引用的 `$ENV:VAR` 已设置，凭据质询会发往攻击者；连接名还可伪装成用户信任的全局名（如 `dev`）。

**修复建议**: workspace scope 连接首次使用时在工具返回中显著标注"来自工作区文件"（已有 scope 字段，但可在 description/引导中强调）；或工作区连接默认不可用、需在全局配置/设置页显式 allowlist。

### M5 配置解析失败时 GUI 保存会清空全部连接

**位置**: `src/rpc/routes.ts:150-156` — `readGlobalFile` 解析失败静默返回 `{connections: []}`，随后 `saveConnection` → `writeGlobalFile` 整体覆写。

用户编辑器半保存/文件被锁/JSON 语法错误时，任何一次 GUI 保存都会**静默丢弃文件里其余全部连接（含密文密码）**。

**修复**: 文件存在但读取/解析失败时拒绝保存（返回错误让用户先修复），或保存前备份 `.bak`。

### M6 `extraParams` 可覆盖安全相关驱动选项

**位置**: `src/db/pool.ts:61` — `...(spec.extraParams ?? {})` spread 在最后

可覆盖 host/port/user/password/database 及驱动安全选项；zod 仅限 string 值，而 mysql2 对 `multipleStatements` 等按真值判断，`"true"` 即生效（开多语句虽仍被文本级网关拦截，但属无谓扩大攻击面；`ssl` 覆盖同理）。

**修复**: denylist 冻结关键键（multipleStatements/ssl/stream/localInfile/timezone 之外的连接类字段），或在 schema 文档明示风险。

### M7 mysql2 查询超时是"客户端假超时"

**位置**: `src/tools/metadata.ts:34,39`（`pool.query({sql, timeout})`）；已核实 `node_modules/mysql2/lib/commands/query.js:346-368` —— 超时仅向回调抛 `Query inactivity timeout`，**不终止服务器端执行、不断连接**。

影响：`db_execute` 15s 超时报错后，长跑写语句仍可能在服务器端完成——工具返回"失败"而数据已变更；`db_query` 的 COUNT(*) 估算（data.ts:110）也会二次执行同一查询。

**修复**: 文档/审计如实注明；可选对超时连接执行 `KILL QUERY <id>` 或销毁该连接。

## 五、实测确认的安全面（做对了的）

- **多语句/会话语句拦截**（真实 classifySql 验证）：`SELECT 1; DELETE FROM t` 双通道拒绝；`USE/SET/SET NAMES`（含解析失败形态）、`SELECT … INTO OUTFILE/DUMPFILE/@var` 全部 blocked；`KILL/DO/HANDLER/TABLE/FLUSH/RESET/PURGE/UNLOCK` 兜底归 unknown→拒绝或需确认；`GRANT→unknown`、`CREATE USER→ddl`。
- **无假阳性**：`UNION [ALL]`、`WITH … SELECT` 正确归 read（不会误伤常用查询）；`WITH … DELETE/UPDATE` 正确归 write。
- **密码体系**：schema 强制 `$ENV/enc`（strict zod）；`bin/encrypt.js` 离线生成不经对话；密钥损坏 fail-loud 不静默轮换（hardening.spec 覆盖）；解密失败不泄内容；GUI 不回显；`sanitize/sanitizeSql` 统一打码 `$ENV/enc` 引用形态；工具与 RPC 出参 0 凭据字段。
- **confirmToken**：HMAC(连接名+语句哈希+过期) + 一次性台账 + `timingSafeEqual`；换语句/换连接/过期/重放均拒（confirm.spec 全覆盖）。
- **资源与输出治理**：行数 200/字节 1MB/单元格 4096 三重截断；RPC body 1MB 上限；审计 30 天滚动 + 队列化 + 每日清理；方法 405/403/404 语义正确。
- **注释安全**：兜底 SELECT 的 LIMIT 注入用派生表包装，防尾注释吞 LIMIT（AST 路径由 sqlify 再生文本追加）。

## 七、修复记录（同轮完成）

### H1 已修复 — EXPLAIN 双层加固（`src/safety/classify.ts`）

- **AST 层**：新增导出 `explainInnerIsRead(nodeType)`；`classifySql` 对 `explain` 节点检查内层语句（node-sql-parser v5.4 存放于 `expr` 属性）——内层非只读（write/ddl/unknown/缺失）时整句归 `unknown` + `blocked`，拒绝按只读处理；EXPLAIN 节点的 `into` 检查同时覆盖 `expr.into`（`EXPLAIN SELECT … INTO OUTFILE` 无法再借道 explain 节点逃逸）。
- **兜底正则层**：新增 `splitExplain()` 剥离 `EXPLAIN` 与其修饰符（`ANALYZE`/`FORMAT=x`/`EXTENDED`/`PARTITIONS`），按内层动词分类：
  - 内层为 read 动词或 `FOR CONNECTION n` → 维持 `read`；
  - `EXPLAIN ANALYZE <写/DDL>`（MariaDB 会实际执行）→ `blocked: true`，任何通道拒绝；
  - `EXPLAIN <写/DDL>`（仅显示执行计划）→ `unknown`/dangerous：只读通道拒绝，写入通道按高危确认闭环；
  - 其余不可识别内层 → `unknown`（最高风险）。
- **测试**：`tests/safety.spec.ts` 新增 "EXPLAIN hardening" 6 例（blocked/dangerous/放行/CTE-DELETE/INTO OUTFILE/AST 守卫单测），断言不依赖具体解析路径，解析器升级也安全。

### H2 已修复 — 确认闭环接入宿主人工审批

- **新增 `src/safety/approval.ts`**：`RequestHumanApproval` 类型（duck-type 宿主 `ApprovalService`，服务 id `'approval'`，非 npm 依赖、无新增包）。
- **`src/index.ts`**：`approvalRequester(ctx)` 惰性解析宿主审批服务——`ctx.get('approval')` 缺失/非函数/调用抛错/未知结果 → 一律 `'unavailable'`；`'rejected'/'cancelled'/'allowed-once'` 原样传递。
- **`src/tools/data.ts`（db_execute 高危门）**：无效/缺失 confirmToken 时先请求宿主人工审批（携带 agent/callId/signal/风险摘要）：
  - `allowed-once` → 执行，审计 `confirmed: true, approval: 'host-approval'`；
  - `rejected/cancelled` → 以 `user-rejected` 拒绝且**不签发令牌**（人工否决不可被自签重试绕过；再次尝试须重新触发审批提示）；
  - `unavailable`（宿主无审批服务/无应答方）→ 退回 PRD FR-9 令牌闭环（拒绝响应携带 confirmToken），并在风险说明中明示退回模式——这是 PRD 风险 #2 已接受的残余风险，仅在无审批通道环境可达。
  - 有效 confirmToken 仍可直接执行（令牌路径不重复打扰审批）。
- **审计**：`AuditEntry` 新增 `approval?: 'host-approval' | 'confirm-token'`，成功与失败条目均记录确认来源；`user-rejected` 计入 `refused` 状态。
- **工具描述**同步更新（审批提示优先、拒绝不回传令牌）。
- **测试**：新增 `tests/approval.spec.ts` 6 例——allowed-once 执行+审计断言、rejected/cancelled 无令牌、无服务退回令牌、服务抛错退回令牌、有效令牌不触发审批。

`sanitizeSql` 新增 4 个形态：`IDENTIFIED BY '…'`（单/双引号）、`PASSWORD('…')`、`SET PASSWORD [FOR …] = '…'`。

### M4 — 工作区同名覆盖可见化（`src/config/store.ts`）

`resolveConnections` 在工作区连接覆盖同名全局连接时向 warnings 推送显著提示（含工作区文件路径），经 `db_list_connections` 与 GUI 警告条透出。解析语义不变（工作区仍优先），零破坏性。

### M5 — 损坏配置拒绝变更（`src/rpc/routes.ts`）

`readGlobalFile` 区分"文件不存在（照常空起）"与"存在但不可读/非法 JSON（返回 error）"；`connections.save/delete` 命中 error 即拒绝并说明"为避免覆盖丢失现有连接"，文件保持原样。`saveConnection`/`deleteConnection` 导出供测试（`tests/rpc-mutation.spec.ts`：损坏 JSON 拒绝+文件不动、正常保存/删除不受影响）。

### M6 — extraParams 加固（`src/db/pool.ts` + `src/config/schema.ts`）

- `toMysqlOptions`：extraParams 改为**先**展开，host/port/user/password/database/池策略/TLS 后置 —— 核心字段永不可被覆盖；
- schema 层拒绝危险键（大小写不敏感）：`host/port/user/password/database/socketPath/ssl/multipleStatements/stream/localInfile/infileStreamFactory/authSwitchHandler`，命中即整条连接校验失败并给出可读警告（salvage 路径跳过该条）；常规调优参数（timezone/charset/dateStrings 等）不受影响。

### M7 — 假超时如实化（`src/db/errors.ts`）

`classifyDbError` 对 mysql2 客户端 inactivity 超时（`Query inactivity timeout`）附加明示："该超时由客户端判定，服务器端语句可能仍在执行"，建议 KILL 会话并核对实际结果。

### 使用影响说明

- 最明显的正向变化：**INSERT/REPLACE 不再每条要求确认**，写数据往返大幅减少；
- 拦截性变化仅两处：全局配置文件损坏时 GUI 保存/删除会被拒绝（提示先修复）；在 extraParams 里滥用危险驱动选项的旧配置，其连接会被跳过并给出警告；
- 其余修复（M2/M3/M4/M7）仅影响错误文案、审计内容与警告可见性，不改变任何操作语义。
